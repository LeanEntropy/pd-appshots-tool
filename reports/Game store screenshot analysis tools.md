# Assemble the pipeline yourself; the recipe step doesn't exist

**Bottom line:** every part of this system except the one that matters most already exists as free, usable code. Downloading screenshots is solved. You can call Apple's free iTunes Lookup API directly, and one of the maintained Google Play scraper libraries covers Android. Classification and marketing-layer analysis are best handled by one hosted vision-model call per screenshot that returns a strict JSON schema. That is cheaper and simpler than self-hosting Qwen3-VL, PaddleOCR or Grounded-SAM-2 for a few hundred images. **No tool, open source or commercial, turns a set of competitor screenshots into an ordered list of "screen type + marketing layer" to replicate.** That analysis-to-recipe step is the gap you would build. Stora.sh comes closest, and it is closed-source SaaS. Your earlier ChatGPT research was mostly accurate: all 11 named projects exist. Its errors are in the details: AppStoreCat's data model and tech stack, the claim that facundoolano's Google Play scraper is "unmaintained", PaddleOCR's fit for stylized game fonts, and OmniParser's relevance. It also missed Apple's free Lookup API, Gemini's built-in bounding-box output, the most popular screenshot-generator repos, and the Game UI Database and GameRefinery as sources for a screen-type taxonomy.

## Download: Apple's free Lookup API beats every scraper

For iOS, **call `itunes.apple.com/lookup?id=…&country=…` directly.** It returns `screenshotUrls` and `ipadScreenshotUrls` as ordered arrays of mzstatic image URLs, with no key and no extra library. A live test confirmed this. The stale `app-store-scraper` package wraps the same endpoint, so it adds nothing. The gaps reported in its issues (empty arrays for some new apps, missing newer device sizes) come from Apple's API itself, so check completeness for each competitor. For Google Play, use **facundoolano/google-play-scraper** for maturity or **@mradex77/google-play-scraper** for TypeScript typing and daily live tests. Both return a `screenshots` array. **One thing is unverified: whether either keeps Play listing order or separates tablet from phone screenshots.** Your requirement depends on order, so test this on day one against a live listing. If you want device-grouped iOS screenshots without handling it yourself, AppTweak's metadata endpoint takes a `device=iphone|ipad|android` parameter ([AppTweak API](https://developers.apptweak.com/reference/app-metadata)), but it is paid. 42matters starts at **$650/mo** ([pricing](https://42matters.com/pricing)). No open-source repo found does "bulk-download competitor screenshots in listing order" as its main job. You write about 50 lines of glue code on top of the libraries above.

## Analysis: one schema-constrained vision call per screenshot

Classification (step 2) and marketing-layer analysis (step 3) fit in **a single hosted vision-model call per screenshot that returns a Pydantic or Zod schema**. That is how Stora built its version: AI SDK `generateObject` with a Zod schema that returns a pattern label plus up to two normalized bounding boxes ([changelog](https://stora.sh/changelog)). Claude supports JSON-schema structured output natively ([docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). **Gemini is the only hosted model with documented built-in bounding-box output** (`[y_min,x_min,y_max,x_max]`, 0–1000) and zero-shot masks ([Google docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/bounding-box-detection)), so use it if you need boxes for bands or characters. Image input is billed at roughly width×height/750 tokens ([guide](https://www.developersdigest.tech/blog/claude-vision-api-production-guide)), and batch processing costs half ([pricing roundup](https://www.finout.io/blog/anthropic-api-pricing)). A few hundred screenshots should therefore cost **tens of dollars at most**. That is my estimate from token pricing, not a measured benchmark. It is far less work than renting a GPU for Qwen3-VL. For the schema layer, **Instructor** is the default in Python ([2026 roundup](https://dev.to/thedailyagent/top-5-structured-output-libraries-for-llms-in-2026-48g0)); in TypeScript, use Zod with the AI SDK.

Deterministic tools add little, but they are cheap and reliable. **k-means clustering or ColorThief** extracts the palette and band colors as exact hex values ([color-thief-py](https://github.com/fengsp/color-thief-py)), which the model can't guarantee. **rembg with BiRefNet** cuts out character art. It is MIT-licensed, while its rival BRIA RMBG-2.0 is non-commercial only ([rembg](https://github.com/danielgatis/rembg), [comparison](https://www.bestaiweb.ai/how-to-build-a-production-background-removal-pipeline-with-bria-rmbg-2-0-photoroom-api-and-rembg-in-2026/)). **No trained device-frame detector exists.** Mockup tools detect frames by matching aspect ratios ([frames](https://github.com/bunlongheng/frames)), so let the vision model label "device frame yes/no". **LayerD** (ICCV 2025) can split a flattened design into layers ([repo](https://github.com/CyberAgentAILab/LayerD)), but it is research code and not needed to *describe* a marketing layer.

## What the prior research missed: taxonomies, renderers and near-competitors

The bigger gap is the **taxonomy**. Apple, Google and the A/B-testing vendors publish no standard list of screenshot types. Stora's labels (hero value prop, social proof, feature showcase) are its own. Two resources can seed your screen types. The **Game UI Database** has 55,000+ game UI screenshots from 1,300+ games, tagged by screen type: HUD/gameplay, shop/monetization, upgrades and unlocks, collection, results, dialogue ([site](https://www.gameuidatabase.com/)). Its reuse license is unverified. **GameRefinery** tracks 260 features across 52 subgenres with 70,000+ example screenshots ([GameRefinery](https://www.gamerefinery.com/genre-taxonomy-update-april-2021/)). It classifies *what gameplay is shown*, which is a different axis from a screenshot's *marketing role*. Keep both axes in your schema. **CGL-Dataset** labels 60,548 posters with four element types (logo, text, underlay, embellishment) ([HF](https://huggingface.co/datasets/creative-graphic-design/CGL-Dataset)). That maps closely onto "copy / band / decoration" for the marketing layer. The academic UI-screen datasets (Rico, Enrico's 20 topics, MASC's 10 classes) classify raw app UI, not store marketing screenshots ([Enrico](https://github.com/luileito/enrico)). No dataset labels store screenshots by marketing overlay.

On rendering, it missed the market leader. **ParthJadhav/app-store-screenshots** (MIT, ~7,000 stars, pushed 2026-09-26) is a Next.js agent skill with 18 styles and copy formulas for each slide role ([GitHub API](https://api.github.com/repos/ParthJadhav/app-store-screenshots)). Other MIT alternatives: **Shotluma**, which runs in the browser with your own API key ([repo](https://github.com/EndersonPro/shotluma)), and **YUZU-Hub/appscreen** (2.1k stars, iOS only) ([repo](https://github.com/YUZU-Hub/appscreen)). Closer competitors it missed: **AppTweak's AI Screenshot Search**, which detects UI elements, text and characters in competitor screenshots ([AppTweak](https://www.apptweak.com/en/aso-blog/ai-screenshot-library-find-instant-creative-inspiration)); **Drazel** ($14/mo), which OCRs competitor screenshot captions and ships an MCP server ([Drazel](https://drazel.store/alternatives/sensor-tower)); and **AppMockup's free Screenshot Analyzer**, which scores screenshots 0–100 but does not classify types ([analyzer](https://appmockupgenerator.com/screenshot-analyzer)). None of them outputs an ordered recipe. ASO guides still describe checking a competitor's screen order as manual analyst work ([618media](https://618media.com/en/blog/competitor-screenshots-for-aso-insights/)).

## Recommended build stack for a solo developer

| Stage | Use | Skip for v1 |
|---|---|---|
| 1. Ingest | iTunes Lookup API over plain HTTP (iOS); `google-play-scraper` or `@mradex77/google-play-scraper` (Android); rewrite the size token in the URL for high-res; store `{app, store, device, locale, position, url, local_path}` yourself | AppStoreCat fork, Apify/SerpApi/42matters |
| 2. Classify | One vision call per image with a fixed enum: gameplay, key art/splash, character/roster, progression/upgrade tree, metagame/base, social/PvP, event/live-ops, shop/offer, feature callout, social proof/awards. Seed it from the Game UI Database and Stora's labels | Fine-tuning on Enrico/MASC |
| 3. Marketing layer | Same call with an Instructor/Zod schema: caption text and position, band/banner shape and position, device frame yes/no, character art placement, layout (e.g., "top caption + full-bleed gameplay"), mood. Add k-means hex palette; use Gemini only if you need boxes | Self-hosted Qwen3-VL, Grounded-SAM-2, OmniParser, LayerD |
| 4. Recipe | A text-only LLM call over the per-position JSON from all competitors: find the most common type and layer at slot 1, 2, 3…, flag where competitors differ, output an ordered list of 8–10 screens | none |
| 5. Render (optional) | Feed the recipe into ParthJadhav/app-store-screenshots or LeeHueeng/store-screenshots | building your own renderer |

Language: Python if you want Instructor and rembg. TypeScript if you want the Play scrapers, Zod and the AI SDK in one runtime, which is Stora's stack. Model choice: Claude Sonnet or Gemini for the per-image call, run through the Batch API. Budget the first week for two checks: whether Play order is preserved, and how well the model reads stylized captions on 20 screenshots you have labeled by hand.

## Conclusion

The build risk is not the tooling. It is the **taxonomy and the aggregation logic**. Downloading and per-image analysis are commodity work in 2026. What competitors can't easily copy is a stable label set for game screenshots plus the rule that turns ten competitors' slot-by-slot choices into one recommended sequence. Design that schema before writing any scraper code. A closed SaaS (Stora) already sells the per-image half, and the generator repos are crowded, so the recipe step is the only part of this system that is new.

Two open risks remain. Neither store's rules on promotional text were checked against Apple's or Google's own pages. And a recipe that copies the *most common* competitor sequence finds what is normal, not what converts. Treat the output as a starting point for A/B tests, not a finished answer.
