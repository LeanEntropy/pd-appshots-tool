# Review: plan-layout-wireframes (gpt-5.6-sol)

Date: 2026-09-28. Reviewer: gpt-5.6-sol via Codex CLI (read-only; the sandbox could not read files, so the plan, PILLARS, plan-reports 3B/3C/11 and the relevant code were passed on stdin). Plan reviewed: docs/plan-layout-wireframes.md (first draft).

## Findings (verbatim)

1. **High — The “layout never breaks the core reading” behavior cannot be implemented with the current `validatedCall`.** A combined strict Zod schema fails as one unit: if `layout` is invalid, `value` is `null`, so the valid core reading is unavailable to save. After retries, both are dropped. **Fix:** parse a permissive envelope first, validate core and layout separately, cache the raw successful provider response, and allow core-only persistence when layout validation fails.

2. **High — Repair-loop counts contradict the existing code.** The plan promises “one repair attempt,” but `MAX_REPAIRS = 2` permits the original call plus two repairs. It also describes layout-only repair, while the existing loop regenerates the entire answer. **Fix:** add an explicit repair limit and validation scope for the combined call, or change the plan, cost cap, timing estimate, and benchmark criterion to two repairs.

3. **High — Keeping the analysis key unchanged creates heterogeneous records under one supposedly content-addressed key.** With the same key, old records contain no layout while new records contain `layout.v1`; changing `layout.v1` later would still address the same record path. This contradicts “content-addressed,” “never recomputed,” and the current `PipelineSpec` rule that the key represents everything an analysis contains. **Fix:** keep the core analysis key stable as approved, but give the layout an independent content-addressed key/sidecar referenced by the analysis record. If it must be embedded, define atomic keyed add-on slots rather than treating the whole record as one immutable value.

4. **High — The proposed record update is unsafe under concurrency.** The shown `writeStoredRecord` performs a read-independent whole-file overwrite and exposes no lock or merge. Backfill, a normal analysis run, or two projects can overwrite another writer’s layout, provenance, identity refresh, or newer fields. Saying it is “written under the record lock” is unsupported by the supplied code. **Fix:** identify the real locking API and specify an atomic read–merge–write under a per-image/per-analysis-key lock, preserving `paidBy`, existing layout versions, and unrelated fields. Add a two-writer test.

5. **High — Reviewer behavior does not fit the current pipeline.** `currentPipeline` assigns the same `fullAnalysis` prompt version to producer and reviewer. The plan instead gives the producer the combined schema and reviewer the core-only schema without defining separate prompt/schema keys. Also, retaining the producer layout after adjudication can leave `capture` and `textRef` pointing into a different settled core reading. **Fix:** add distinct producer and review prompt contracts/cache keys, then revalidate or remap the layout against the final settled core; otherwise mark it missing.

6. **High — A/B behavior violates the authoritative one-variable rule.** The plan says a card merely warns if code creates more than one change. R2b requires such a test to be rejected. A “typical layout” may simultaneously move a band, resize text, add a cut-out, change framing, and alter overlay share. **Fix:** generate exactly one declared composition intervention with a defined atomic scope, or reject the variant and produce the next valid candidate. Never publish an invalid test with a warning.

7. **High — The benchmark does not test the most important failure modes.** Four curated images are too few to validate composites, repeated same-role elements, absent marketing layers, pure art, non-band overlays, multiple text blocks, and producer/reviewer/adjudication interactions. Only one sample lacks a cached core baseline. **Fix:** keep the four-image paid gate, but add free fake-provider cases and synthetic fixtures for those structural cases; include at least one multi-capture sample in the paid set if none of the four exercises capture indexing adequately.

8. **Medium — Accuracy matching and missing-value scoring are underspecified and gameable.** “Greatest overlap” does not require one-to-one matching, so multiple predictions could match one answer element. Scaling up non-applicable measurement components can let a simple image dominate, and treatment of absent headline/subline/logo is undefined. **Fix:** specify one-to-one optimal matching, penalties for duplicates, exact denominators for absent roles, and separate required scores for element detection, text, and measurement instead of relying only on a weighted total.

9. **Medium — The answer key is not sufficiently independent.** It is reduced from the same detailed agent breakdowns that motivated the schema, then translation meaning is judged by the same GPT reviewer family used to check the key. This measures agreement with the chosen reduction more than real layout usefulness. **Fix:** freeze explicit human-checkable reduction rules first, have two independent reductions resolved before seeing outputs, and score translation against fixed reference meanings rather than a post-run model judgment.

10. **Medium — The cost comparison mixes total cost and incremental cost.** The benchmark budget of $0.85–$1.10 appears plausible for four fresh full calls, but the rollout claim of only +$0.04–$0.07 per image is not supported by comparing fresh combined calls with cached historical answers. Repair calls could also exceed the $1.20 total unless the cap is enforced across the whole benchmark. **Fix:** report paired baseline and combined runs using identical images, model settings, and prompt context; show total and incremental cost separately, include repairs, and enforce one aggregate benchmark budget before each call.

11. **Medium — The measurement claims exceed what the proposed algorithms can reliably determine.** Colour-distance segmentation cannot generally isolate outlined, shadowed, textured, or gradient-backed text; “lowest pixel per column” is unreliable for multi-line and non-Latin text; mean foreground/background colours do not produce a valid contrast ratio. Cut-out boxes make overlay share a potentially large upper bound. **Fix:** narrow v1 to robust edge and geometry measurements, define masks and confidence calibration, label box-union coverage explicitly as an upper bound, and keep uncertain text height/contrast out of recommendations until validated.

12. **Medium — Noise-control rules contradict the uses.** Section 6 says unmeasured estimates are not used for tilt or overlay patterns, while section 5 promises layout statistics and briefs even where pixel measurement fails. Section 3 also says low-quality measurements retain the model value. **Fix:** define eligibility per metric: measured-only for aggregate numeric claims; estimated values may be displayed per image but excluded from consensus and recommendation evidence. State the minimum eligible `n`.

13. **Medium — Core and layout fields can disagree without a reconciliation rule.** The core already contains marketing masks, text regions, elements, coverage, captures, and headline. The new layout duplicates these with roles, boxes, `textRef`, coverage, and text. No rule decides which wins when they conflict. **Fix:** define invariants and canonical ownership: core owns transcription and capture identity; layout references them; pixel facts own measurable geometry. Validate headline/text references, capture indices, marketing presence, and coverage consistency.

14. **Medium — Several schema details are ambiguous.** It is unclear whether `capture` is zero- or one-based, how “none” is represented in a strict schema, whether `covers` may reference only screenshot IDs, what `text` contains for marketing elements when `textRef` is present, and how polygonal/tilted elements are represented by a box plus angle. **Fix:** specify exact JSON types, null conventions, indexing, reference constraints, coordinate/rotation origin, and examples for single capture, composite, pure art, and no marketing layer.

15. **Medium — Pixel-storage rules are incomplete and partly inconsistent with existing storage.** The plan invents a filename containing both measuring version and layout answer key, but the current `pixelsKey` API accepts one version string and legacy mode ignores that version entirely, reusing one facts filename. “Write-once” behavior and collision handling are not described. **Fix:** extend the storage interface with a typed layout-measure key, support both library and legacy modes correctly, verify existing content on collision, and never write through direct filesystem paths.

16. **Medium — Backfill detection and reuse are not designed.** Current `isUsable` only checks the core schema and final reading, so a layout-less record remains done and no ordinary run will request its layout. The plan does not specify how backfill completion, partial failures, layout-version staleness, or resumability are determined. **Fix:** add an independent layout status/version check and job state keyed by image plus layout contract; the UI should distinguish current, missing, failed, and outdated layouts.

17. **Medium — Milestone L0 is not actually isolated as described.** Running the “real production combined call” requires changes to call schemas, prompt composition, validation, and likely cache routing, yet L0 lists only token-count changes in `providers.ts` among existing files. It also builds substantial production modules before the benchmark’s go/no-go. **Fix:** describe L0 as an isolated benchmark harness using production interfaces, list every temporary integration change, and keep it from changing current pipeline behavior or records.

18. **Low — Language-fit results would not be portable or typographically authoritative.** System fonts vary by machine, and width alone does not handle line breaking, shaping, punctuation rules, vertical metrics, or artist-selected fonts. The average-character fallback is especially weak for recommendations like “shrink to 77%.” **Fix:** bundle licensed test fonts or record the exact font/version, use a shaping/layout engine, label results as approximate, and avoid exact shrink percentages when using fallback metrics.

19. **Low — The user-facing plan contains internal implementation language and too many decisions without consequences.** Terms such as analysis key, answer key, schema contract, R2b, and L1 are not explained, while D2 hides the record-consistency tradeoff and D4 offers a “hard maximum 10” that conflicts with the recommended cap of 8. **Fix:** add a short plain-language decision summary explaining what changes, what costs money, what can become stale, and what happens on failure; present 8 versus 10 as one explicit choice.

20. **Low — Priority ordering conflicts with PILLARS.** PDF work appears in L2 alongside core on-screen wireframes even though PDF is explicitly low priority, while actionable briefs do not arrive until L4. **Fix:** defer PDF integration until after patterns and briefs work in HTML; align delivery as capture/storage → patterns → actionable briefs/readability → optional PDF polish → future history.
