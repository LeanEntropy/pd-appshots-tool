# Review: plan-analysis-speed (gpt-5.6-sol)

Date: 2026-09-29. Reviewer: gpt-5.6-sol via `codex exec -m gpt-5.6-sol -s read-only --skip-git-repo-check --ephemeral` (plan, measurements and requirements passed inline). Reviewed the first draft; decisions on each finding are in section 14 of `docs/plan-analysis-speed.md`.

1. **Major — §1, §9: spend cap is not yet provably exact.** “Reserve then replace with real cost” needs an atomic, crash-safe ledger; the attempt log alone does not prevent two workers reading the same remaining balance. Retries, producer/reviewer/settle calls, fallback calls, and benchmark repairs must share the same cap. `--max-budget-usd` should not be assumed to prevent overshoot without a measured guarantee. **Fix:** specify a serialized reservation transaction, durable reservation IDs, startup reconciliation for abandoned reservations, conservative per-call ceilings, and tests for simultaneous starts, crashes, retries, and costs reported above reservation. Stop launching when the remaining amount cannot fund the minimum safe ceiling.

2. **Major — §1: “exact stop” semantics are weaker than claimed.** The plan lets up to five paid calls continue after Stop, potentially spending all their reservations. That may be acceptable, but it is not an immediate spend stop. Process cancellation and Windows child-process behavior are unspecified. **Fix:** explicitly define Stop as “stop scheduling, drain in-flight calls,” show the maximum reserved cost that may still be spent, and offer a separate cancel-in-flight action only if partial outputs and child-tree termination are safe. Test Stop during producer, review, settle, backoff, and retry.

3. **Major — §2, §10: the inline-image CLI path is speculative and sequenced incorrectly.** S1 implements it before the paid spike in S3 proves that the installed Claude CLI accepts image content blocks, schema output, and `--tools ""` together. The required output/input flags, base64 limits, validation behavior, and fallback invocation are not pinned down. **Fix:** make the spike the first capped benchmark operation and gate S1 on a captured successful command/result. Define the exact stream-JSON envelope and CLI version. Preserve the current path until proven.

4. **Major — §1–2: Windows process requirements are missing.** The requirements explicitly say spawn `claude -p` directly, not through `cmd.exe`; the plan only discusses arguments and temp names. **Fix:** state and test `spawn(executable, args, {shell:false})`, independent stdin/stdout per worker, executable resolution for Windows shims, timeout handling, and safe termination of the spawned process tree. No command-string construction.

5. **Major — §3, §5: cache-key compatibility is unsafe/contradictory.** The plan says S1’s key remains unchanged despite transport/prompt-order changes, then broadly accepts the previous pipeline key under v7/v4. Directional compatibility is not defined, and lean expansion invents `confidence: 1`, `scale: "medium"`, and `breaksFrame: false`, turning “not measured” into false facts. Measured colours further change semantics. **Fix:** use explicit capability/version metadata and directional compatibility: old complete records may satisfy lean consumers, but lean records must not satisfy consumers requiring omitted/model-derived fields. Preserve omitted values as absent, never fabricated. Keep measured-colour provenance/version separate and test shared-library lookup both directions.

6. **Major — §6, §9: “existing records stay valid” conflicts with recomputed colour inputs.** Existing analyses remain accepted, yet their colour statistics and potentially report/recommendation inputs change. The plan marks only AI-written parts stale “if a colour pattern changes,” which can miss other changed downstream inputs. **Fix:** version derived facts independently, deterministically recompute them for all records, and invalidate every dependent artifact through dependency keys. State precisely which stored records remain valid and which reports become stale.

7. **Major — §9: the benchmark cannot prove no accuracy loss.** Five baseline reruns versus ten new runs are not paired equally; existing analyses are noisy model outputs, not an answer key. “Noise floor minus one image” permits a ten-percentage-point loss, while rare fields may occur once or not at all. Free text receives no independent accuracy assessment. **Fix:** use paired baseline and candidate runs on all ten images, blind human adjudication against the screenshots for disagreements, field-level counts/coverage, and zero-regression gates for critical/rare fields. Describe this as a limited acceptance benchmark, not statistical proof; require a larger post-launch shadow sample before claiming no loss.

8. **Major — §9: downstream gate does not meet the stated requirement.** The requirement says patterns/verdict/recommendation **inputs** must remain unchanged. The gate permits differences whenever the noise run shows similar variation and only blocks changed verdict or fits/different markers. Tags, pattern statistics, key points, screenshot lines, and recommendation inputs may change silently. **Fix:** compare normalized downstream input objects field-by-field and require equality except explicitly approved derived-colour changes; separately compare outputs. Any unexplained input change is no-go.

9. **Major — §7, §9: model assignment violates the rules.** Text comparison analyzes screenshot crops using Opus 5.5, while the requirements mandate Fable 5.1 for screenshot analysis, no Sonnet, and GPT only as reviewer. **Fix:** use Fable 5.1 for crop analysis; restrict GPT to review/second opinion and document every model-role mapping in the benchmark.

10. **Major — §8: the near-duplicate thresholds are fitted but not validated for false positives.** The evidence contains mostly known “same screen” answers; it does not establish safety against different images whose changes fall inside broad text/band boxes. Auto-deciding ≤0.5% removes user control precisely where false matches are costly. Adjustable thresholds also invalidate the claimed performance. **Fix:** validate on labeled same and different pairs, including badges/characters inside bands and tiny changes outside; report false-positive/negative rates. Add an uncertainty margin and keep those cases in R4. Show auto-decisions for review and require confirmation when validation coverage is absent.

11. **Minor — §1, §3: prompt-cache warm-up is asserted, not demonstrated.** Starting workers when the first answer “starts” does not prove the cache write is committed or that separate CLI processes share the prefix cache; volatile CLI context may alter the prefix. **Fix:** gate parallel release on observed cache-write completion if available, then verify cache-read tokens in the benchmark. Fall back to ordinary concurrency if warming provides no measured benefit.

12. **Major — §§1, 10–12: several governing constraints are not implemented as acceptance criteria.** The plan does not explicitly require pre-AI counts and approval for every normal run, full resumability after crash, provider/storage/jobs interfaces, shared-library behavior under concurrent projects, ≤300 lines per file, strict TypeScript, or Biome. The layout conflict is also understated: an “add-on that never changes the key” cannot safely make missing layout data appear present. **Fix:** add milestone gates and tests for each constraint; store layout as a separately versioned add-on record, and merge the overlapping provider/pipeline changes only after the in-flight branch is integrated.

**Overall verdict:** **No-go as written**; the optimization direction is sound, but cap/stop correctness, key provenance, model compliance, and benchmark validity need material revision before implementation.
