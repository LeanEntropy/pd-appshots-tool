# Review: plan-knowledge-base.md (gpt-5.6-sol, 2026-09-29)

Reviewer: gpt-5.6-sol via `codex exec -s read-only --ephemeral`, plan passed inline. One review, on the finished draft (user directive). What was applied or declined is at the end of `docs/plan-knowledge-base.md`.

Bottom line: the plan has a strong structure, but it is not implementable as written. The largest problems are a direct exception to the user’s strict trust rule, unreliable “code enforcement” claims, underspecified evidence independence, retrieval that can miss decisive evidence, and materially understated cost/evaluation scope.

## Findings

| Severity | Section | Problem | Fix |
|---|---|---|---|
| **Major** | 0, 2.4, 13, decision 1 | The “official store fact” exception directly contradicts the strict rule: every trusted claim requires more than one independent organisation. A Google or Apple page alone must therefore remain unverified, even when it is authoritative about its own store. | Remove the exception. Represent single-source official facts as `unverified_official` or simply `unverified`; they may be quoted as “Google currently documents…” but not promoted to corroborated fact. Seek an independent observation or test for corroboration. If the user wants an exception, identify it explicitly as a requested change to the requirement, not as compliance. |
| **Major** | 2.3–2.4 | Organisation and `origin` fields do not make independence reliably computable. Syndication, agencies publishing vendor studies, subsidiaries, commissioned research, and multiple sources using an undisclosed common dataset cannot be determined from URLs and organisation IDs alone. | Add reviewed evidence-cluster fields such as `evidenceOriginId`, `datasetId`, `fundedBy`, `commissionedBy`, and `independenceReviewedBy`. Code may count pre-reviewed clusters, but must not claim to discover independence automatically. Unknown provenance should conservatively count once. |
| **Major** | 2.2–2.4 | Trust is assigned to an entire entry, but an entry can contain a claim plus multiple “specifics.” Two sources may support different fragments without independently supporting the same proposition. That would falsely produce corroboration. | Make each entry one atomic proposition. Attach source-support records to exact claim facets or structured facts. Trust must be calculated per proposition from sources that support that same proposition and scope. Reject compound claims during validation/review. |
| **Major** | 2.4 | “A counter-source of equal or higher trust” is circular and underspecified. Trust belongs to entries, while `counterEvidence` is described as sources; the plan does not define what claim those sources support, their scope, or how their independence is counted. | Model counterclaims as first-class atomic entries linked by `contradictsEntryIds`. Calculate trust independently for each side. Mark a claim contested when an applicable counterclaim crosses a documented threshold; do not compare an entry’s trust with a raw source. |
| **Major** | 0, 3, 4.4 | Code cannot reliably reject “facts stated from unverified entries,” determine whether prose “rests on” a reference, or detect that a KB claim semantically contradicts local data. Those are semantic judgements, not deterministic checks. Dropping a reference after failure can leave the unsupported prose intact. | Separate enforceable structural checks from model review. Require structured `claimType`, `evidenceBasis`, `dataFactIds`, `kbRefs`, and `conflictIds`. Generate visible prose from these fields where feasible. On invalid evidence, regenerate or remove the entire claim—not only its citation. Describe semantic checks as reviewer checks with measured error rates, not code guarantees. |
| **Major** | 4.4, 10 | The “every number must appear in data or cited specifics” check will produce both false passes and false failures. It cannot distinguish dates, positions, ranges, percentages, derived values, formatted equivalents, script-specific numerals, or a number used in the wrong context. Matching the same token does not prove support. | Do not validate arbitrary prose by number matching. Put quantitative assertions in structured fields containing value, unit, denominator, derivation and evidence ID. Render them deterministically. Limit text linting to a warning for unexpected numeric tokens. |
| **Major** | 3, 4.2 | The model receives claims and truncated specifics but no source-support notes or URLs. It therefore cannot check whether sources support a claim, distinguish primary from copied evidence, or accurately explain/cite evidence. The recommendation reviewer receives the same already-compressed representation. | Give the evidence-review call the exact source-support excerpts/notes, source type, date, organisation and scope. Synthesis may use compact, pre-approved propositions, but citation-support review must operate on richer evidence records. Never truncate away qualifiers or denominators. |
| **Major** | 3, 4.1 | Retrieval is driven mainly by tags generated from already-detected dimensions. It will miss relevant constraints or counter-evidence whose tags were not activated. Multiplicative scoring also overweights narrow market notes regardless of evidence quality and can reduce broadly applicable established evidence below weak local material. | Add task-specific required facets and negative/counterclaim retrieval. Use an explicit additive ranking with calibrated components and minimum eligibility thresholds. Retrieve a balanced set by facet—store constraint, applicable heuristic, counter-evidence, market note—not merely global score order. Test retrieval recall against a hand-labelled query set before integration. |
| **Major** | 3, 4.1 | “Regulation entries always included” can overflow the stated token budget, and relevance is not sufficiently defined. Regional notes may also be retrieved for countries where the regional generalisation is wrong. | Reserve a bounded safety/policy allocation, deduplicate propositions and fail visibly when mandatory material exceeds it. Require explicit country applicability for regulatory entries. Treat region-to-country applicability as a claim needing its own evidence, not an automatic scope match. |
| **Major** | 3, 4.3 | “Data first” is too absolute. Competitor prevalence shows convention, not effectiveness. A strong majority can reflect copied practice or poor-performing pages. Following it by default conflicts with the purpose of an evidence-backed expert. | Distinguish descriptive competitor evidence from causal outcome evidence. Clear local prevalence should not be silently overruled, but neither should it automatically decide the recommendation. Output: observed convention, outcome evidence, confidence, decision rationale and test opportunity. Own valid experiments may outrank prevalence. |
| **Major** | 4.3 | “Thin data” is defined partly as fewer than five games, while the project apparently has eight competitors per country. No statistical or coverage rationale is given, and “strong” inherits unspecified thresholds from other plans. | Define clear evidence states using known-value count, denominator, concentration, missingness and stability. Reference exact versioned thresholds. Validate them with saved datasets rather than choosing five ad hoc. |
| **Major** | 4.5, 9 | An own experiment becomes “clear local evidence” merely because it was recorded. The schema lacks allocation, sample size, confidence/credible interval, run completeness, novelty effects and overlapping changes. “Winner” or Play’s displayed range is insufficient. | Store the full experiment design and statistical result. Classify results as valid, inconclusive or invalid using store-specific rules. Only a valid result may become local evidence. Never automatically attach a project result as a new independent source to global KB claims; route proposed generalisation through inbox, independence review and approval. |
| **Major** | 5 | Several “code-only” detectors are not reliably code-only from the stated inputs. Actual pre-scroll visibility depends on device, store surface, UI version, video placement and locale—not only image dimensions. Caption legibility requires reliable OCR geometry and rendered display size. Panoramic-edge similarity is prone to false positives. Policy risk across languages cannot be safely covered by patterns alone. | Treat these as separate detector research tasks with defined inputs, gold-labelled validation sets, precision/recall targets and explicit “unknown” outcomes. Rename “first impression” to a narrower measurable proxy unless actual store layouts are captured. Policy detection should be advisory and versioned per policy/locale. |
| **Major** | 6 | A hash of current files does not let an old report rebuild the old KB. Once files change, the old content is gone unless the repository revision or an immutable snapshot is retained. | Store the git commit/content-addressed KB bundle with the report, or archive immutable KB versions. Record prompt version, retrieval-map version and renderer version too. Define how historical reports resolve that bundle outside a developer checkout. |
| **Major** | 6–7 | The KB is described as shared by all projects but also as repo-local files committed with code. That is contradictory operationally: projects may use different repository revisions and approvals, while runtime writes to a deployed repo may be impossible. | Choose an ownership model: bundled read-only KB releases, or a separately versioned data store/package. Keep approval workflow and runtime project results outside application source. Define promotion from inbox to a signed/versioned KB release. |
| **Major** | 7 | “Second agent, adversarial” and GPT source checks are presented as assurance, but there is no reproducible research protocol or evidence capture. A model cannot verify a source it has not been given in full, and source notes written by the first researcher can repeat its mistake. | Archive permitted evidence excerpts or structured observations with retrieval dates. Require the second pass to inspect the source independently. Add deterministic schema/link checks plus human approval for consequential claims. Record reviewer identity/model and prompt version. |
| **Major** | 10 | The evaluation is not truly blind. The GPT judge receives the KB slice, which can reveal which output used it, and the same model family creates/reviews/judges the work. The rubric lacks factual-claim-level adjudication and inter-rater handling. Three reports are also too small to validate nine markets and multiple step types. | Hide treatment indicators and do not give the judge treatment-only material unless both arms receive an identical evidence packet. Add claim-level factual review by a human, randomise output order per step, measure agreement, define tie handling, and include representative cases for every enabled step and market/script risk. Use a fixed evaluation set plus adversarial conflict/thin-data cases. |
| **Major** | 0, 3, 10, 12 | Cost is materially understated. Nine country-advice calls alone can consume roughly 27k KB tokens before recommendations, reviews, A/B tests, pattern wording, group analysis and outputs. “4 to 8 calls” conflicts with “3k per country” and separate review calls. The evaluation is not “about 3 extra synthesis runs”; rebuilding three reports may require dozens of calls. | Produce a call graph per report type with minimum/typical/maximum calls, input/output tokens, cache assumptions and model prices. Estimate evaluation cost from every duplicated generation and judge call. Set hard per-report and per-refresh spending caps. |
| **Major** | 10 | “Ship only if it wins and adds no errors” is not operational. GPT citation-support target zero cannot be known to be zero, and preference in two of three reports allows broad regressions hidden by aggregation. Repeating once after revision risks tuning to the same tiny test set. | Define measurable gates: human-confirmed unsupported claims, retrieval recall, critical-error count, per-step rubric floors, maximum verbosity/cost regression and market coverage. Keep a held-out evaluation set for the second run. |
| **Minor** | 2.5 | Expiry mechanically lowering trust conflates freshness with independent corroboration. A claim does not lose a source when its review date passes; instead, confidence in current applicability decreases. | Keep evidence count/trust and freshness as separate dimensions. Block stale current-state claims where appropriate, but do not relabel a two-source claim as one-source. |
| **Minor** | 2.5 | A/B cases never expire even though store UI, attribution, experiment tooling and market conditions change. Ranking them lower after three years does not prevent obsolete mechanics from being used. | Give cases an applicability period and store/UI version. Old cases can remain historical evidence but should not support current mechanics without current corroboration. |
| **Minor** | 3 | Recommendation review gets “the same slice … by the ids used.” If this literally means only cited IDs, it cannot detect cherry-picking or an omitted counterclaim. | Give review all eligible retrieved entries, mandatory counterclaims and the selection log—not only used citations. |
| **Minor** | 3–4 | The plan says citations appear with source names and dates, but the model only sees handles and source counts. This is workable only if rendering is entirely deterministic; that boundary is not clearly specified. | State that source labels, dates, links and trust badges are always generated from the registry by code. The model should output handles only. |
| **Minor** | 5, 12 | K5 comes after evaluation even though new detectors are supposed to improve the facts used for retrieval and recommendations. Evaluating before them makes the evaluated system different from the eventual one. | Either exclude detectors from the initial KB release explicitly, or implement and validate the required detectors before the final acceptance evaluation. Re-evaluate whenever a detector materially changes recommendation inputs. |
| **Minor** | 8 | User-editable token budgets can silently remove necessary evidence and make output quality non-comparable, while mandatory entries can ignore the budget. | Offer tested presets or a global cost ceiling. Preserve minimum evidence allocations and show when a call could not fit required evidence. |
| **Minor** | 12 | The milestones put the user-facing result capture and usable Knowledge page late, while approval is required during K1 and own-result learning is a core requirement. The interim workflow may become disposable implementation work. | Build a minimal review/approval interface or stable import/export format early. Split K6 into minimal result capture before rollout and richer management UI later. |
| **Minor** | 13 | Important risks are missing: malicious or misleading source text, broken/link-rotted evidence, licensing/quotation constraints, locale misclassification, regulatory liability, source registry merge errors, and KB changes causing widespread cache invalidation. | Add guards for source provenance, archived metadata, quotation limits, locale validation, advisory legal wording, merge review and estimated recomputation impact before publishing a KB version. |
| **Minor** | 14 | The decisions omit several choices that materially change design: strict-rule exception, prevalence versus outcome evidence, KB ownership/deployment, acceptable human review burden, and cost ceiling. | Replace decision 1 with a compliance-preserving choice and add explicit decisions for those architecture and operating-policy questions. |

## Verdict

**Rework.**

The content taxonomy, atomic retrieval intent, versioned prompts, structured references, data-first conflict surfacing and staged rollout are good foundations. But the plan should not move into research or implementation until the trust-rule exception is removed, semantic “code checks” are narrowed to enforceable structures, evidence independence is manually reviewable rather than inferred, the storage/versioning model is made real, and costs plus evaluation are recalculated from the actual call graph.
