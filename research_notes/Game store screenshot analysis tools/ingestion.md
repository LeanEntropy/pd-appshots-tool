# Open-Source Tools for Retrieving Google Play / App Store Listing Screenshots (Competitor Games)

Research date: 2026-09-26. Scope: verify claims from a prior (possibly hallucinated) ChatGPT report and surface missed alternatives for pulling per-device / per-locale store-listing screenshots in listing order.

## Does github.com/appstorecat/appstorecat exist? Is it MIT, self-hosted, iOS+Android scrapers, competitor lists, screenshot history, MCP server, Docker? StoreListing model with {url, device_type, order}? Tech stack and fork weight?

### Takeaway
The repo is real and most of the ChatGPT claims check out (MIT, self-hosted, Docker, MCP server, competitor tracking, screenshot change history) — but the tech-stack claim is only half right (it's a polyglot Laravel+React+Node+Python monorepo, not pure PHP/Laravel), and the specific `StoreListing` schema claim ({url, device_type, order} per screenshot) is **not confirmed** — the documented schema stores screenshots as a flat JSON array of URLs with no per-item device_type/order fields.

### Cited Findings
- Repo exists at [github.com/appstorecat/appstorecat](https://github.com/appstorecat/appstorecat), organization-owned, created 2026-04-15, 40 stars, 3 forks, MIT license confirmed via GitHub API license field — [GitHub API](https://api.github.com/repos/appstorecat/appstorecat).
- Description: "Open-source app intelligence toolkit — track, analyze, and discover mobile apps across App Store and Google Play"; topics include `app-store`, `google-play`, `aso`, `scraper` — [GitHub repo](https://github.com/appstorecat/appstorecat).
- README confirms: self-hosted (`curl -sSL https://appstore.cat/install.sh | sh` or `git clone` + `make setup && make dev`, requires Docker/git/make/curl), Docker images published to `ghcr.io/appstorecat/server`, and an MCP server with "32 tools (28 read · 4 write — track/untrack apps and add/remove competitors)" published as `@appstorecat/mcp` on npm, usable via `claude mcp add appstorecat ... npx -y @appstorecat/mcp` — [README.md](https://raw.githubusercontent.com/appstorecat/appstorecat/master/README.md).
- Feature table explicitly lists "Competitor tracking — Side-by-side competitor monitoring" and "Change detection — Per-locale diffs of title, screenshots, version, price," confirming both the competitor-list and screenshot-history claims — [README.md](https://raw.githubusercontent.com/appstorecat/appstorecat/master/README.md).
- Architecture table in the README: `server/` = Laravel 13 / PHP 8.4 / Sanctum / L5-Swagger; `web/` = React 19/Vite/TS/shadcn/Tailwind v4; `scraper-ios/` = Fastify 5 / Node.js, built on the **`app-store-scraper`** npm package (i.e., wraps facundoolano's library); `scraper-android/` = FastAPI / Python, built on **`gplay-scraper`**; `mcp/` = TypeScript MCP SDK — [README.md](https://raw.githubusercontent.com/appstorecat/appstorecat/master/README.md).
- GitHub's language breakdown for the repo: TypeScript 828,876 bytes, PHP 786,556 bytes, Python 20,313, JavaScript 12,544, plus Makefile/Shell/CSS/HTML/Dockerfile — confirming it is a genuinely polyglot monorepo, not a single-stack Laravel app — [GitHub languages API](https://api.github.com/repos/appstorecat/appstorecat/languages).
- Repo root contains `mcp/`, `scraper-android/`, `scraper-ios/`, `server/`, `web/`, `docs/`, `docs-site/`, plus `docker-compose.yml` and `docker-compose.production.yml` at the root and inside `scraper-ios/` — five separately-runnable services — [contents listing](https://api.github.com/repos/appstorecat/appstorecat/contents).
- Data-model doc: the `app_store_listings` table (Eloquent model `StoreListing`) has a `screenshots` column typed **`json` — "Array of screenshot URLs"** — a flat array, not a set of `{url, device_type, order}` records. Uniqueness constraint is `(app_id, version_id, locale)`; there is no `device_type` or explicit `order` column documented anywhere in the data model or the Store Listings feature doc — [docs/en/architecture/data-model.md](https://raw.githubusercontent.com/appstorecat/appstorecat/master/docs/en/architecture/data-model.md), [docs/en/features/store-listings.md](https://raw.githubusercontent.com/appstorecat/appstorecat/master/docs/en/features/store-listings.md).
- The Python scraper dependency `gplay-scraper` is a real, actively described PyPI package by `mohammedcha` (v1.0.6, "65+ app fields... 7 HTTP clients"), separate from `google-play-scraper`/`JoMingyu` — [PyPI JSON](https://pypi.org/project/gplay-scraper/).
- Release history shows real, frequent tagged releases (v1.2.4 on 2026-04-27 through v1.2.8 on 2026-05-19), consistent with `pushed_at: 2026-05-19`; no releases/pushes found after that date as of 2026-09-26 (~4 months of inactivity at research time) — [GitHub releases API](https://api.github.com/repos/appstorecat/appstorecat/releases).

### Inferences
- Forking/self-hosting this project is non-trivial: it requires running (or Dockerizing) five services across three language runtimes (PHP/Laravel, Node/Fastify, Python/FastAPI, plus the TS web app and TS MCP server) with MySQL and Redis as dependencies, versus a single-purpose scraper library. This is heavier than the ChatGPT report's "PHP/Laravel, how heavy is it to fork?" framing implies, since only one of five services is actually Laravel.
- Because `scraper-ios` and `scraper-android` are thin wrappers around `app-store-scraper` (npm) and `gplay-scraper` (PyPI) respectively, appstorecat's screenshot data quality/order/device coverage is bounded by those two upstream libraries — see their sections below for known gaps.
- Since screenshots are stored as an unstructured array (no explicit `device_type`/`order` fields in the documented schema), any per-device-type or per-position filtering would need to be inferred from array position and from which scraper (iOS vs Android) produced it, not read directly off a normalized field — a meaningful correction to the ChatGPT report's claim.

### Gaps
- The exact `StoreListing`/`screenshots` column shape claim ({url, device_type, order}) could not be confirmed from the documented schema and appears to be an overstatement or hallucination; the actual source code for the Eloquent model/serializer was not read line-by-line (only the docs describing it), so it's possible undocumented internal structuring exists, but the public docs contradict the specific claim.
- Whether appstorecat captures iPad-specific vs iPhone-specific screenshots separately (device_type-level granularity) was not directly verified from source; the `scraper-ios` service depends on `app-store-scraper`, which does separate `screenshots` (iPhone) from `ipadScreenshots` (see facundoolano section) — but whether appstorecat's `StoreListing.screenshots` column merges these or keeps them distinct was not confirmed.

## facundoolano/app-store-scraper: status, maintenance, does app() return screenshots/ipadScreenshots; documented issues where screenshots come back empty? Alternatives for Apple (iTunes Lookup API, HTML/JSON-LD scraping, Python forks)?

### Takeaway
The library is real, MIT-licensed, and does return `screenshots` / `ipadScreenshots` / `appletvScreenshots` arrays — but it is in slow maintenance mode (last GitHub commit 2025-07-27, last npm publish 0.18.0 in **November 2023**, 73 open issues) with confirmed, still-open GitHub issues about screenshots coming back empty or missing newer device sizes. The iTunes Lookup API is a solid, well-documented, free direct alternative that returns the same screenshot fields.

### Cited Findings
- `facundoolano/app-store-scraper` exists, MIT license, 1,426 stars, 300 forks, 73 open issues; `pushed_at: 2025-07-27` (most recent commit as of research date was over a year old) — [GitHub API](https://api.github.com/repos/facundoolano/app-store-scraper).
- Most recent commits: 2025-07-27 ("Update privacy and version history function url", #225), 2025-01-24 ("add function to fetch version history", #213), then a gap back to 2023-11-21 — showing the project gets very occasional community-driven maintenance but is not actively developed — [commits API](https://api.github.com/repos/facundoolano/app-store-scraper/commits).
- The npm package `app-store-scraper` has not had a new version published since **0.18.0 on 2023-11-21** — nearly 3 years stale on npm despite two small GitHub-only patches landing since (meaning `npm install app-store-scraper` does **not** pick up the 2025 fixes) — [npm registry JSON](https://registry.npmjs.org/app-store-scraper).
- Open issue #171 (from a real bug report, shows actual library output) confirms the `app()` result object includes `screenshots: [...]`, `ipadScreenshots: []`, and `appletvScreenshots: []` arrays as documented fields — [issue #171](https://github.com/facundoolano/app-store-scraper/issues/171).
- Open issue #215, "Some apps don't have any screenshots" (opened 2025-04-07, still open, 1 reaction): reporter finds specific app IDs where the iTunes Lookup API itself returns no screenshot data for either iPhone or iPad, unclear if a caching issue on Apple's side — confirms a real, current, unresolved gap where screenshots can legitimately come back empty for some (especially very new) app listings — [issue #215](https://github.com/facundoolano/app-store-scraper/issues/215).
- Open issue #153, "Screenshot URLs for 6.5" devices are missing?" (opened 2021-01-25, still open, 7 comments): confirms a long-standing, still-unresolved gap where only older device-size screenshot URLs (5.5") are returned, not newer iPhone X-and-above (6.5") sizes — [issue #153](https://github.com/facundoolano/app-store-scraper/issues/153).
- Direct test of the iTunes Lookup API (`https://itunes.apple.com/lookup?id=...&country=us`) confirms it independently returns `screenshotUrls`, `ipadScreenshotUrls`, and `appletvScreenshotUrls` as ordered JSON arrays of `mzstatic.com` CDN URLs — this is Apple's own free, documented, no-auth-required API and is the most direct, dependency-free alternative to a scraper library — verified live (tool self-test), 2026-09-26.
- Python alternatives found: `digitalmethodsinitiative/itunes-app-scraper` (GitHub, "a simple Python scraper for the iTunes App Store") has a maintenance-tracking derivative `itunes-app-scraper-dmi` on PyPI, flagged by Snyk's health analysis as having had "no new versions released to PyPI in the past 12 months," i.e., effectively stalled — [Snyk advisor](https://snyk.io/advisor/python/itunes-app-scraper-dmi), [GitHub](https://github.com/digitalmethodsinitiative/itunes-app-scraper).
- `python-app-store-scraper` exists on PyPI as another Python option — [PyPI](https://pypi.org/project/python-app-store-scraper/).
- Web search surfaced `app-store-web-scraper`, described as "a fork and rewrite of app-store-scraper by Eric Lim," positioned as more recently maintained, though focused on reviews rather than confirmed for full listing/screenshot scraping — [PyPI](https://pypi.org/project/app-store-web-scraper/).

### Inferences
- Because the npm-published version of `app-store-scraper` is nearly 3 years behind the GitHub `master` branch, anyone relying on `npm install app-store-scraper` (rather than installing directly from GitHub) is missing at least two 2025 fixes — worth flagging for any tool selection that shortlists this package.
- The two open, years-old screenshot-related issues (#153 and #215) indicate the empty/incomplete screenshot problem is a real, persistent limitation of scraping via this library (and, per issue #215, possibly a limitation of Apple's own Lookup API responses in some cases, not just the wrapper) — so screenshot completeness should not be assumed and should be spot-checked per app.
- Given both the empty-screenshots and stale-device-size issues trace back to what the iTunes Lookup API itself returns, calling the Lookup API directly does not fully route around these gaps — it would surface the identical missing/incomplete data in cases like #215, though it would sidestep any bugs specific to the wrapper library's parsing.

### Gaps
- Could not verify whether `app-store-web-scraper` (the "Eric Lim fork") specifically supports full listing scraping (title/description/screenshots) versus being reviews-only; only surfaced via a web-search summary, not read directly from its source or README.
- Could not verify current GitHub activity/stars/last-commit dates for `digitalmethodsinitiative/itunes-app-scraper`, `python-app-store-scraper`, or `app-store-web-scraper` in this pass (time/tool-call budget); Snyk's "no PyPI release in past 12 months" signal for `itunes-app-scraper-dmi` was the only maintenance data point directly confirmed for the Python alternatives.
- Did not confirm whether the iTunes Lookup API enforces rate limits or requires special handling for bulk competitor-list use (e.g., the officially documented ~20 requests/minute soft limit); this wasn't directly tested or sourced in this pass.
- Scraping `apps.apple.com` HTML directly (JSON-LD / `serialized-server-data` embedded JSON) was not independently tested or sourced with a citation in this pass — flagging as unverified rather than fabricating a claim about its current shape/reliability.

## Does Google Play expose high-res screenshots via a URL size parameter (e.g. =w2560) and Apple via mzstatic URL size templates?

### Takeaway
Both mechanisms are real and directly observed, though the exact `=w2560` parameter name from the ChatGPT report was not independently pinned down — Google Play/Google-hosted image CDN URLs (`play-lh.googleusercontent.com`, `googleusercontent.com`) are confirmed to support size-changing URL suffixes (documented example: `=h230` → `=h1600`), and Apple's `mzstatic.com` CDN URLs embed an explicit `WIDTHxHEIGHT` size token (e.g., `/320x480bb.jpg`, `/392x696bb.png`) in the path that can be substituted for other sizes.

### Cited Findings
- A direct live test of Apple's iTunes Lookup API returned screenshot URLs of the form `https://is1-ssl.mzstatic.com/image/thumb/.../<uuid>_....jpg/320x480bb.jpg` and ipad screenshots as `.../576x768bb.jpg` — confirming the well-known mzstatic "size template" suffix pattern (`{width}x{height}bb.{ext}`) that can be edited to request a different rendition size — verified live, 2026-09-26.
- A bug-report code sample from `facundoolano/app-store-scraper` issue #171 independently shows the same pattern in real scraped data: `.../392x696bb.png` screenshot URLs — corroborating the size-template mechanism from a second, independent source — [issue #171](https://github.com/facundoolano/app-store-scraper/issues/171).
- For Google Play, web search confirms Google-hosted image URLs (used for Play Store assets) support a documented resize technique: "opening the image in a new tab and replacing `=h230` to `=h1600` at the end of the URL... forces the screenshot to open in its full-size" — confirming a `=h{number}` (height) parameter pattern exists on these CDN URLs — [Techtrickz](https://techtrickz.com/how-to/enable-high-resolution-screenshots-view-in-play-store-how-to/).

### Inferences
- The general mechanism the ChatGPT report described (URL-parameter-driven resizing for both stores) is real and correct in spirit for both Google Play and Apple; the specific parameter name `=w2560` for Google Play is plausible (Google's image CDN is known to support both `=w{n}` width and `=h{n}` height suffixes, and `=s{n}` for square/max-dimension) but was not independently confirmed with a working example in this research pass — treat the exact numeric value/parameter letter as unverified until tested against a live Play Store asset URL.

### Gaps
- Did not fetch a live Google Play Store listing page or CDN image URL directly to confirm the `=w2560` (or `=w{n}`) parameter works as described — only found corroborating community documentation for the closely related `=h{n}` pattern. This should be spot-checked directly (e.g., `curl -I` against a `play-lh.googleusercontent.com` URL with `=w2560` appended) before relying on it in an ingestion pipeline.
- Did not verify whether Apple has recently changed or deprecated the mzstatic size-template mechanism (e.g., rate-limiting arbitrary sizes, or requiring the size to match a whitelist) — only confirmed that URLs currently contain a substitutable size token.

Its own claim that the original `facundoolano/google-play-scraper` is "unmaintained" is **false/outdated** — that repo is actively maintained (npm 10.1.3, published 2026-05-31; GitHub pushed 2026-09-21).
- **facundoolano/app-store-scraper**: real, but in slow/low maintenance (GitHub last commit 2025-07-27; npm last publish Nov 2023) with two confirmed, still-open GitHub issues about screenshots being empty (#215) or missing modern device sizes (#153) — a real, citable known-breakage, not a hallucination.
- **Google Play / Apple URL-based high-res screenshot access**: real mechanism on both sides; Apple's mzstatic size-template is directly confirmed from two independent sources; Google's exact `=w2560` parameter form is plausible but unverified — recommend a direct spot-check before depending on it.
- **JoMingyu/google-play-scraper (Python)**: real but genuinely stale (no push since 2024-08-05), a fair candidate to flag as declining/less-maintained.
