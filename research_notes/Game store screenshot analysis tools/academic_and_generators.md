# Academic Research and Open-Source Screenshot Generators for App/Game Store Screenshot Recipes

## Are there papers/datasets specifically classifying app store screenshots by screen type, and do any include released code/data?

### Takeaway
Yes — several released, code/data-backed datasets exist for classifying mobile UI screenshots by design/topic/screen type (Rico, Enrico, MASC, Aurora), but none of them are purpose-built for *app store marketing screenshots* (i.e., the curated, overlay-annotated images developers upload to a store listing). They classify raw app UI screens (settings, list, login, etc.), which is a related but distinct problem from classifying a store screenshot's "screen type + marketing overlay."

### Cited Findings
- **Rico** is the foundational large-scale dataset: design data from 9.7k+ Android apps spanning 27 categories, exposing visual/textual/structural/interactive properties of 72k+ unique UI screens, built via combined crowdsourcing + runtime automated mining — [Rico (ACM DL)](https://dl.acm.org/doi/10.1145/3126594.3126651), [Interaction Mining project page](https://interactionmining.org/rico)
- **Enrico** ("Enhanced Rico"): 1,460 UIs manually curated from a 10k random Rico sample and classified into **20 design topic categories**; includes screenshots (540×960 JPG), semantic wireframe PNGs, semantic annotation JSON, and view hierarchies; screenshot-based deep learning models reached 95% AUC / ~75% accuracy vs. 5% for a random classifier. Code/data released on GitHub — [Enrico project page](https://userinterfaces.aalto.fi/enrico/), [GitHub luileito/enrico](https://github.com/luileito/enrico), [ACM paper](https://dl.acm.org/doi/fullHtml/10.1145/3406324.3410710)
- **Aurora** dataset: derived by sampling from Rico, with 1,370 UI screens manually grouped into 21 semantic categories — [MASC search summary](https://www.researchsquare.com/article/rs-3786876/v1) (cites Aurora as related work; Aurora's own primary paper was not independently verified in this pass — see Gaps)
- **MASC (Mobile App Screens Classification)**: 7,065 images sourced from Rico, manually classified into **10 unique screen classes**; paper proposes an ML framework (feature extraction on visual/text/keyword elements) and reports XGBoost/SVM-Linear as best performers. Dataset and preprint are both released — [Research Square preprint](https://www.researchsquare.com/article/rs-3786876/v1), [Zenodo record (dataset)](https://zenodo.org/records/14783065), [Kaggle mirror](https://www.kaggle.com/datasets/alihmed/masc-dataset), [ResearchGate PDF](https://www.researchgate.net/publication/376914983_MASC_A_Dataset_for_the_Development_and_Classification_of_Mobile_Applications_Screens)
- **RICO-ICON**: a Rico-derived dataset of 120,000+ cropped icons for training icon/graphic classifiers; **VINS**: a separate Mobile GUI Images dataset — both cited as supporting datasets for GUI element/screen classification work — [GUI classification search summary, citing VINS/RICO-ICON](https://ar5iv.labs.arxiv.org/html/2105.11941)
- Google's **ScreenQA** (86K QA pairs over ~35K Rico screenshots) and **Screen2Words** (112,085 natural-language screen summaries for 22,417 Rico screens, UIST'21) are released with code/data, but target screen *comprehension/summarization*, not marketing-screenshot recipe generation — [screen_qa GitHub](https://github.com/google-research-datasets/screen_qa), [screen2words GitHub](https://github.com/google-research-datasets/screen2words)
- Google's **Screen Annotation** dataset (paired with the ScreenAI vision-language model) provides UI element type/location/OCR/description annotations over mobile screenshots — [screen_annotation GitHub](https://github.com/google-research-datasets/screen_annotation)
- Apple's **"Understanding Screen Relationships from Screenshots of Smartphone Applications"** (Apple ML Research) trained models on 1,000+ iPhone apps' screenshots for screen-similarity and screen-transition understanding — not released as an open dataset as far as this search could confirm — [Apple ML Research page](https://machinelearning.apple.com/research/screen-relationships), [ACM version](https://dl.acm.org/doi/fullHtml/10.1145/3490099.3511109)
- A 2026-dated preprint, **"Fusing UI Structure & Semantics for Feature-Oriented App Screen Retrieval & Clustering"**, addresses app screen retrieval/clustering by feature, relevant to grouping competitor screens by function — [arXiv 2608.08880](https://arxiv.org/pdf/2608.08880)
- General mobile-screenshot clustering: **"Guess What's on my Screen? Clustering Smartphone Screenshots with Active Learning"** clusters arbitrary smartphone screenshots (not store-listing images specifically) — [arXiv 1901.02701](https://arxiv.org/pdf/1901.02701)

### Inferences
- No dataset found is annotated at the specific granularity the target system needs (screen-type + marketing-overlay-type per store screenshot slide, e.g., "gameplay screen + character-callout banner" or "IAP/shop screen + angled percentage-off band"). Enrico's 20 categories and MASC's 10 classes are the closest proxies for a general "screen type" taxonomy and could be adapted/fine-tuned, but would need a new annotation layer for marketing overlays specific to store screenshots.
- Because Enrico, MASC, Rico, ScreenQA, Screen2Words, and Screen Annotation are all built from real in-app UI captures (not curated marketing screenshots), a system targeting *store* screenshots would likely need its own small labeled set — these datasets are best used as pretraining/transfer-learning bases or as a taxonomy starting point, not as drop-in training data.

### Gaps
- Could not verify a primary/independent source for the **Aurora** dataset (21 categories, 1,370 screens) beyond a secondary mention inside the MASC paper's related work — its original paper/authors/release location were not confirmed in this pass.
- Could not find any peer-reviewed dataset or paper that annotates *App Store/Google Play listing screenshots themselves* (as opposed to general in-app UI screens) by screen type or marketing-overlay type.
- Could not find MSR/ICSE-specific papers mining app **store screenshots** (the search surfaced MSR/ICSE papers on bug-report screenshots and general app-UI mining, e.g. GuiEvo, ImageR, "Inferring Questions from Programming Screenshots" — these are adjacent but not about store-listing screenshot marketing content) — [MSR/ICSE search results](https://2024.msrconf.org/track/msr-2024-technical-papers), [GuiEvo/ImageR/etc. found via search, not independently verified for store-screenshot relevance]

## Are there game-specific UI screen classification datasets/taxonomies?

### Takeaway
No academic dataset specifically classifies *mobile game* store screenshots or even general in-game UI screens by type with released ground truth; the closest resources are (a) game genre classification from icon/screenshot images, which is a different task, and (b) the **Game UI Database**, a large curated (non-academic) practical reference cataloguing 55,000+ game UI screenshots by screen type — useful as a taxonomy source but not a downloadable ML dataset with labels/code.

### Cited Findings
- **Game UI Database** (gameuidatabase.com): a curated practical reference with 1,300+ games and 55,000+ UI screenshots, browsable by screen type (gameplay/HUD, menus, mode & screen select, results screens, monetization/premium stores, upgrades & unlocks, collection systems, dialogue, modals/popups), animation, layout, and color — [Game UI Database](https://www.gameuidatabase.com/), [screen type index example](https://gameuidatabase.com/index.php?scrn=904&set=1&tag=6)
- **Game Genre Classification from Icon and Screenshot Images Using CNNs**: dataset of 147,182 mobile games across 9 categories (Racing, Educational, Puzzle, Board, Action, Casino, Sports, Word, Music); CNN classification achieved 40.3% (icon) / 46.7% (screenshot) accuracy — task is genre inference, not screen-type/overlay classification — [ACM paper](https://dx.doi.org/10.1145/3375959.3375988), [ResearchGate](https://www.researchgate.net/publication/339306610_Game_Genre_Classification_from_Icon_and_Screenshot_Images_Using_Convolutional_Neural_Networks)
- A separate CNN benchmark using MobileNet/DenseNet/EfficientNetB0/B2/B3 across 8,796 games and 170,881 screenshots reported EfficientNetB3 at ~74% average genre-classification accuracy — again genre, not screen-type — (found via aggregated search summary; primary paper URL not independently captured, see Gaps)
- **PlayMyData**: a curated multi-platform video game metadata dataset (not screenshot-focused per se) — [arXiv 2401.08561](https://arxiv.org/pdf/2401.08561)

### Inferences
- The Game UI Database's screen-type taxonomy (menus, HUD, monetization/shop, results, mode-select, dialogue/modals, etc.) is a strong candidate reference taxonomy to seed a "screen type" label set for a game-screenshot recipe system, even though it is not an ML-ready dataset (no bulk downloadable labeled export or code was found/verified).
- Genre-classification research (game icon/screenshot → genre) is not directly reusable for the target task (identifying screen type + overlay per screenshot position) but confirms CNN-based screenshot classification is a well-trodden, workable approach at the whole-image level.

### Gaps
- Could not verify whether the Game UI Database offers bulk data export, an API, or a license permitting reuse of its taxonomy/images for training — this needs direct confirmation from the site's terms.
- Could not locate the primary source (only an aggregated summary) for the 8,796-game/170,881-screenshot EfficientNet benchmark; treat that figure as unverified pending the original paper.
- No paper found that classifies mobile game *store* screenshots (vs. generic app screenshots or in-game UI) by marketing-overlay type (e.g., banner, angled percentage band, character callout).

## Is there research/datasets on ad creative or poster layout analysis that could be reused for marketing-overlay layout?

### Takeaway
Yes — a well-developed line of work on content-aware graphic/poster layout generation exists with released datasets and code, most notably CGL-Dataset (60,548 posters) and several follow-on GAN/diffusion/LLM-based layout generators; these are strong candidates for reuse in generating or scoring marketing-overlay placement (text/logo/banner positioning) on top of a game screenshot.

### Cited Findings
- **CGL-Dataset**: released alongside "Composition-aware Graphic Layout GAN for Visual-Textual Presentation Designs" (IJCAI 2022); consists of 60,548 (in some reports, paired inpainted) posters with layout annotations covering 4 element types — logos, text, underlays, embellishments — each with category + coordinates; also ~121,000 clean product images. Code and data released — [arXiv 2205.00303](https://arxiv.org/abs/2205.00303), [IJCAI proceedings](https://www.ijcai.org/proceedings/2022/692), [GitHub minzhouGithub/CGL-GAN](https://github.com/minzhouGithub/CGL-GAN), [Hugging Face dataset](https://huggingface.co/datasets/creative-graphic-design/CGL-Dataset)
- **CGL-Dataset V2**: extension for advertising poster layout generation, with 60,548 training + 1,035 test samples — [search summary citing CGL-Dataset V2](https://huggingface.co/collections/creative-graphic-design/poster-generation-dataset)
- **Relation-Aware Diffusion Model for Controllable Poster Layout Generation** — a diffusion-based approach for controllable poster layout (element placement relative to underlying image content) — [arXiv 2306.09086](https://arxiv.org/pdf/2306.09086)
- **CALayoutDM**: "Two-stage Content-Aware Layout Generation for Poster Designs" — [PDF, USTC](http://staff.ustc.edu.cn/~lszhuang/Doc/2023-MM-CALayoutDM.pdf)
- **PosterLLaVa**: a unified multimodal layout generator built on an LLM, for graphic design layout generation — [arXiv 2406.02884](https://arxiv.org/pdf/2406.02884)
- **GAN-based Domain Adaptation for Image-aware Layout Generation in Advertising Poster Design**: extends the poster-layout GAN line of work with domain adaptation — [arXiv 2604.07409](https://arxiv.org/html/2604.07409)
- **PRISM: Learning Design Knowledge from Data for Stylistic Design Improvement** — learns design knowledge from data to improve layout/style, relevant to scoring or refining a generated screenshot's visual design — [arXiv 2601.11747](https://arxiv.org/pdf/2601.11747)

### Inferences
- CGL-Dataset's element taxonomy (logo/text/underlay/embellishment with bounding boxes) maps well onto the marketing-overlay concept needed for a screenshot recipe (banner text, callout shapes, angled bands, logo placement) — this is likely the single most directly transferable academic resource found for the "overlay" half of the recipe (screen type being the other half, covered by Rico/Enrico/MASC-style work).
- The 2022–2026 span of poster-layout papers (GAN → diffusion → LLM-based) shows this is an active research area; a recipe system could plausibly fine-tune or prompt an LLM-based layout generator (e.g., PosterLLaVa-style) conditioned on a game screenshot instead of a generic product photo.

### Gaps
- None of the poster-layout papers were found to target *app/game store screenshots* specifically (they're for general advertising posters/e-commerce banners) — applicability to game screenshots (which have existing UI chrome, characters, and HUD elements that a poster background usually lacks) is inferred, not demonstrated in any source found.
- Could not confirm licensing terms for CGL-Dataset (commercial-use restrictions are common for such academic/industrial datasets, e.g. Alibaba-affiliated) — verify before any production reuse.

## What open-source tools already render store screenshots from raw captures + a template/recipe? (verify LeeHueeng/store-screenshots and find alternatives)

### Takeaway
LeeHueeng/store-screenshots exists, is MIT-licensed, and is a small (86-star), locally-run HTML/CSS + headless-Chrome/Playwright renderer with AI-generated copy — but it does not analyze competitors or produce a "recipe." Several more actively developed alternatives exist (ParthJadhav/app-store-screenshots at 7,000+ stars; Shotluma; YUZU-Hub/appscreen), all MIT-licensed and template-flexible, but none of them derive their layout/overlay choices from competitor screenshot analysis — that step is universally absent from the open-source tooling landscape.

### Cited Findings
- **LeeHueeng/store-screenshots** — confirmed to exist. MIT license; ~86 stars, 7 forks, 12 commits (last-commit date not visible in fetched content). Described as "an AI agent skill for Claude Code & Codex" that turns raw screenshots into store-ready App Store/Google Play images. Tech: HTML/CSS composition rendered via headless Chrome (Playwright fallback), shell scripting, `sips`/ImageMagick for verification. Device frames drawn "in pure CSS" for iPhone, iPad, Galaxy, Fold, Flip; background presets are "Modern/Minimal, Pop, and Dark" plus app-color matching; AI-generated marketing copy per screen with user approval; outputs exact App Store (6.9"/6.5" iPhone, iPad) and Google Play (phone/tablet/foldable) sizes. Explicitly local-first: "Nothing leaves your machine. No uploads, no accounts, no watermarks." Does **not** produce competitor-derived recipes/storyboards — [GitHub LeeHueeng/store-screenshots](https://github.com/LeeHueeng/store-screenshots)
- **ParthJadhav/app-store-screenshots** — MIT license; 7,000+ stars, 516 forks, 31 commits. Tech stack: Next.js, React, TypeScript, Tailwind CSS, shadcn/ui, Radix, html-to-image, JSZip, dnd-kit, react-rnd. Positioned as "a skill for AI coding agents" (Claude, Cursor, Windsurf) — the agent is prompted with app context and scaffolds a full editor project with copy + layout. Offers 18 named visual styles, device frames (iPhone, iPad, Android phone/tablet, Play Store feature graphics), palette presets, RTL-aware layouts, draggable/resizable canvas elements. Includes a "copy guidance library" with formulas per slide role and ready lines for 13 app categories, but does **not** auto-analyze competitor decks — [GitHub ParthJadhav/app-store-screenshots](https://github.com/ParthJadhav/app-store-screenshots)
- **Shotluma** (EndersonPro/shotluma, also mirrored at realZachi/shotluma) — MIT-licensed, open-source, "local-first AI App Store screenshot editor." Projects live entirely in-browser (no backend/account); AI features are bring-your-own-key across OpenAI, Anthropic, Google, Qwen, Moonshot; the AI agent drives the same canvas editor a human would (text layers, gradients, shapes, device mockups remain editable afterward). Exports PNG sets in a ZIP at standard iOS resolutions (1290×2796, 1242×2688) — [GitHub EndersonPro/shotluma](https://github.com/EndersonPro/shotluma), [Vercel Community launch post](https://community.vercel.com/t/introducing-shotluma-free-open-source-appstore-screenshot-generator/47440), [shotluma.com](https://shotluma.com/)
- **YUZU-Hub/appscreen** — MIT license; 2.1k stars, 308 forks. Tech: vanilla JavaScript (no framework), HTML5 Canvas for 2D rendering, Three.js for 3D device mockups, IndexedDB for local persistence, JSZip for export, Docker+nginx deployment — notably does **not** use Remotion, Satori, or a headless browser. Supports gradient backgrounds with draggable color stops, 1500+ Google Fonts, per-screenshot settings, multiple output sizes, and AI-powered translation (Claude/OpenAI/Google APIs) for localized exports. Targets iOS App Store only (iPhone 6.9"/6.7"/6.5"/5.5", iPad 12.9"/11", custom sizes) — not positioned for game-specific screenshots — [GitHub YUZU-Hub/appscreen](https://github.com/YUZU-Hub/appscreen), [live demo](https://yuzu-hub.github.io/appscreen/)
- **easy-frame** — a lightweight open-source Swift command-line tool (SwiftUI-based) for framing App Store screenshots, positioned as a fastlane frameit alternative with ~500 lines of forkable/customizable code — [iOS Dev Tools newsletter mention](https://iosdevtools.substack.com/p/ios-dev-tools-easy-frame-sweetpad), related fork [alschmut/easyframecommand](https://github.com/alschmut/easyframecommand)
- Numerous **commercial/closed** alternatives were found but not evaluated for open-source status: Mockly (native Mac GUI, $12.99 one-time), Screenshots.live, ScreenshotWhale, Screenshot Bro, Marteso, AppLaunchpad, AppScreens, AppScreenStudio, AppMockUp Studio, Hotpot, Screenshots.pro, Previewed.app, Screenshot Otter — [comparison roundup](https://appdrift.co/blog/10-best-app-store-screenshots), [fastlane frameit alternatives roundup](https://lagerland-apps.github.io/alternatives/fastlane-frameit/)

### Inferences
- The most template-flexible and actively adopted open-source options (ParthJadhav/app-store-screenshots, Shotluma) are converging on a common pattern: ship as an "agent skill" that an AI coding assistant scaffolds/customizes per project, rather than a traditional standalone SaaS or CLI — this is a notably different distribution model than fastlane frameit's config-file approach, and is relevant if the target system wants to integrate with or emit output compatible with such skills.
- None of the surveyed open-source generators ingest a competitor screenshot set as input to decide screen order/overlay type — they all start from the user's own raw screenshots plus manually chosen (or LLM-authored, but not competitor-derived) copy/style. This confirms a genuine gap: the "recipe" step (turning competitor analysis into an ordered screen-type + overlay plan) is not solved by any existing OSS renderer; renderers only solve the "recipe → pixels" step.

### Gaps
- Could not confirm exact "last commit" dates for LeeHueeng/store-screenshots, ParthJadhav/app-store-screenshots, or YUZU-Hub/appscreen (fetched summaries did not surface commit timestamps) — check directly on GitHub for current activity status as of September 2026.
- Did not independently verify Shotluma's star count/fork count or exact commit recency.
- Did not deep-dive fastlane frameit itself (assumed known/out of scope as the incumbent baseline rather than a "finding"); if needed, its GitHub (fastlane/fastlane) has extensive but config-driven (not visually templated) framing.

## Is there any existing tool that already produces a "screenshot storyboard/recipe" from competitor analysis (the core novel step)?

### Takeaway
No such tool was found, open-source or commercial. Existing ASO platforms let you *view* competitor screenshots side by side, and existing generators let you *render* a screenshot set from your own raw captures — but nothing found automatically infers an ordered screen-type + overlay recipe from a set of competitor store screenshots. This appears to be a genuine, unaddressed gap in both the academic and OSS/commercial landscape.

### Cited Findings
- ASO competitor-analysis tools (ASO.dev, AppTweak, AppLaunchFlow) let users preview all of a competitor's screenshots at once and manually assess "visual style, messaging, and localization," and manually evaluate "how the order of screens is arranged" — this is explicitly framed as manual analyst work, not automated recipe extraction — [618media competitor screenshot analysis guide](https://618media.com/en/blog/competitor-screenshots-for-aso-insights/), [ASO tools comparison](https://appdrift.co/blog/15-best-app-store-optimization-tools)
- Screenshot A/B testing guidance (ScreenMagic, AppLaunchFlow, Shotlingo) confirms the *value* of getting screenshot order/content right — citing that optimized screenshots can shift conversion 20-35%, and that "roughly 60% of the install decision is made right there in the first screenshot" — but these are testing/optimization frameworks for a developer's own listing, not competitor-recipe-extraction tools — [Shotlingo A/B testing framework](https://dev.to/shotlingo/ab-testing-your-app-store-screenshots-a-complete-framework-12nj), [AppTweak 2026 category benchmarks cited](https://www.applaunchflow.com/blog/app-store-screenshot-ab-testing-2026)
- No dedicated "storyboard from competitor screenshots" product, GitHub repo, MCP server, or Claude skill was found in this search pass.

### Inferences
- The market/research gap is specifically in the *analysis-to-recipe* step (competitor screenshots in → ordered {screen type, overlay type} list out), not in rendering (well-served by OSS tools above) or in raw screen-type classification (partially served by Rico/Enrico/MASC-style datasets). A system combining (a) an Enrico/MASC-style or Game-UI-Database-style screen-type classifier, (b) a CGL-Dataset-style overlay/layout element detector, and (c) a renderer akin to ParthJadhav/app-store-screenshots or LeeHueeng/store-screenshots would appear to be a novel combination not currently packaged together anywhere found.

### Gaps
- This finding is a negative result (absence of evidence) rather than a confirmed absence — it's possible a niche or very recent (2026) tool exists that wasn't surfaced by the queries used; recommend a follow-up targeted search closer to build time using terms like "screenshot sequence classifier," "competitor screenshot decomposition," and checking Papers with Code / Hugging Face Spaces directly, which were not exhaustively queried in this pass.
- Did not check ASOMobile, Sensor Tower, data.ai/Appfigures, or Storemaven's *own* internal methodology papers/patents (some ASO vendors publish white papers on screenshot best practices derived from proprietary data) for whether any have a published (even if not open-source) automated storyboard-extraction capability.
